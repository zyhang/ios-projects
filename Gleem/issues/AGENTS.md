# Issues 目录规则（Stillwall / Gleem）

本目录用于记录 **App 已开发完成后的页面与功能问题**，以及需要开发人员按说明调整的修改项。  
每个 issue 是一份给开发看的任务包：说明问题、期望效果、改哪里、配截图/附件。

协作文档使用中文（标识符、API 名、面向用户的英文 UI/商店文案除外）。

---

## 目录结构

```
issues/
├── AGENTS.md                 # 本规则（必须遵守）
├── README.md                 # 索引（可选，便于人工浏览）
└── NNN-简短英文或拼音 slug/   # 一个 issue 一个子文件夹
    ├── README.md             # 开发必读：问题描述与修改说明（必须）
    ├── before/               # 当前错误/待改状态截图（推荐）
    ├── after/                # 期望效果参考图（可选；有设计稿或标注图时放这里）
    └── assets/               # 其它附件（标注图、录屏、日志片段等，按需）
```

### 编号规则

1. **序号递增**：使用三位数字 `001`、`002`、`003`…，从现有最大号 +1 取新号。  
2. **文件夹名格式**：`NNN-short-slug`  
   - 例：`001-home-stats-layout`、`002-setup-permission-copy`  
   - `slug` 用小写英文/数字和连字符，简短表达主题，方便检索。  
3. **一个子文件夹只对应一个 issue**，不要把多个无关问题塞进同一文件夹。  
4. **不要复用已关闭 issue 的序号**；若需返工，新建下一序号并在描述里引用旧 issue。

### 取号方式

创建新 issue 前：

1. 列出 `issues/` 下已有 `NNN-*` 文件夹。  
2. 取最大 `NNN` + 1 作为新序号。  
3. 若目录为空，从 `001` 开始。

## 单个 Issue 必含内容

### `README.md`（必须）

面向开发人员，写清楚 **如何改**，建议结构：

```markdown
# Issue NNN：简短标题

| 字段 | 内容 |
|------|------|
| 状态 | open / in_progress / done / wontfix |
| 优先级 | P0（阻塞发布）/ P1 / P2 |
| 类型 | bug / ui / copy / behavior / docs-sync |
| 影响范围 | 主 App / Safari 扩展 / 设置 / 其它 |
| 相关文档 | 可选：product-charter、screens、design-system 路径 |
| 创建日期 | YYYY-MM-DD |

## 问题现象

（当前实际表现是什么；可引用 before/ 截图）

## 期望结果

（改完后应该怎样；可引用 after/ 或设计稿）

## 修改说明（给开发）

- 具体改哪些界面/文案/逻辑
- 约束与注意点（不要误改的范围、i18n、深色模式、动态字体等）
- 若需同步产品/设计文档，写明要改的文档路径与要点

## 验收标准

- [ ] 可勾选的完成条件 1
- [ ] 可勾选的完成条件 2

## 附件

- `before/xxx.png` — …
- `after/xxx.png` — …
```

### 截图与附件

| 目录/文件 | 何时需要 |
|-----------|----------|
| `before/` | 有真实机/模拟器问题截图时**尽量提供**；文件名有意义，如 `home-overflow.png` |
| `after/` | 有期望 UI、标注图、或对标设计导出时放入 |
| `assets/` | 录屏、日志、对比拼图、额外标注等 |

截图约定：

- 优先 PNG。  
- 文件名小写、连字符，避免空格与中文文件名（说明写在 README 里）。  
- README 中用相对路径引用，例如 `![当前](before/home.png)`。

## 工作流（产品 / Agent / 开发）

### 1. 收录问题（产品或 Agent）

用户提供截图或文字描述后：

1. 按编号规则新建 `NNN-slug/`。  
2. 写入 `README.md`（现象、期望、修改说明、验收标准）。  
3. 将截图归入 `before/` 或 `after/`（及 `assets/`）。  
4. 若问题本质是产品定义变更（而不只是实现偏差），同步更新 `docs/` 中对应文档，并在 issue 的「相关文档」中写明路径与变更摘要。  
5. 有意义的变更完成后：**在 `main` 上 commit 并 push**（遵循仓库根目录 `Agents.md` git 工作流）。

### 2. 开发修改

开发根据 issue 文件夹内容改代码/资源；完成后将 issue 状态改为 `done`，或在 PR/提交说明中引用 `issues/NNN-...`。

### 3. 关闭与归档

- 状态改为 `done` 或 `wontfix` 即可，**不要删除**历史 issue 文件夹（便于回溯）。  
- 不需要单独的 archive 目录，除非 issue 数量极大再议。

---

## Agent 执行约定

在本仓库处理「页面/功能有问题、根据截图改、让开发按说明改」类请求时：

1. **先读本文件**，再创建或更新 issue。  
2. **只通过本目录的递增子文件夹管理 issue**，不要把同类零散说明只写在聊天里而不落盘。  
3. 每个新问题 **一个文件夹**；相关但可独立验收的问题优先拆成多个 issue。  
4. 描述以开发可执行为准：写清改什么、不要只写「不好看」。  
5. 用户丢截图时：保存到对应 issue 的 `before/`（或用户标明为期望图则放 `after/`），并在 README 中引用。  
6. 需要改产品定义时：更新 `docs/` 并在 issue 中交叉引用，避免 issue 与文档长期不一致。  
7. 完成收录后按仓库规则 **commit + push 到 main**。

## 状态枚举

| 状态 | 含义 |
|------|------|
| `open` | 已记录，待开发处理 |
| `in_progress` | 开发进行中 |
| `done` | 已按说明修改并通过验收 |
| `wontfix` | 不修复（需在 README 写明原因） |

---

## 与其它文档的关系

| 文档 | 用途 |
|------|------|
| `docs/product/product-charter.md` | 产品范围与原则（定义变更时改这里） |
| `docs/design/*` | 流程、界面、设计系统（UI/交互偏差对照） |
| `docs/decisions/decision-log.md` | 需要正式决策时记录 |
| **`issues/*`** | **实现侧待改清单与验收材料**（本目录） |

Issue 描述实现差距与改法；产品文档描述「应该是什么」。两者冲突时，先与产品确认，再改文档或改 issue 期望，不要静默选边。
