# 支持、规则运营与事故响应

## 1. 目的

广告拦截产品会持续面对网页变化、规则误伤和平台限制。运营目标不是承诺“永不失效”，而是让问题能够被快速识别、准确归因、安全修复，并让用户知道当前状态。

本文适用于 TestFlight 和正式发布后的：

- `Missed Ad` 与 `Site Broken` 反馈。
- 规则更新、灰度、回滚。
- App 和扩展故障。
- 隐私与安全事件。
- 用户沟通和内部复盘。

## 2. 支持原则

- `Site Broken` 的优先级通常高于 `Missed Ad`。
- 先恢复用户正常浏览，再追求更强拦截。
- 不要求用户默认提供完整 URL、浏览记录、Cookie 或账号信息。
- 不确定根因时明确标注，不把第三方站点变化说成已经修复。
- 所有规则修复都需要可复现步骤、测试结果和回滚路径。
- 用户可自行通过暂停或 Allowlist 立即恢复站点。
- 对 YouTube、X 等动态站点，状态说明必须基于当前验证结果。

## 3. 反馈入口

MVP 提供两个清晰入口：

### 3.1 Missed Ad

适用于：

- 页面仍出现展示广告。
- YouTube Safari 仍播放广告。
- X Safari 仍出现 Promoted Posts。
- Cookie banner、Open in App 或 newsletter 等未被处理。

### 3.2 Site Broken

适用于：

- 页面空白、正文缺失或布局严重损坏。
- 登录、支付、搜索、播放或导航失效。
- 页面循环刷新或明显卡顿。
- 关闭 Gleem 后问题消失。

反馈页面需要在发送前展示实际包含的字段。默认建议字段：

- 用户主动填写的域名与描述。
- 问题类别。
- App 版本、构建号、规则版本。
- 设备类型和系统版本。
- Content Blocker、Gleem Extra 状态。
- 暂停、Allowlist、关闭 Extra 后的验证结果。

截图、完整 URL 和额外诊断仅由用户主动选择附加。

## 4. Issue 分类

建议使用以下字段：

| 字段 | 示例 |
| --- | --- |
| 类型 | `site-broken`、`missed-ad`、`youtube`、`x`、`update`、`privacy` |
| 组件 | App、Content Blocker、Gleem Extra、rules、delivery |
| 环境 | development、staging、production |
| 规则版本 | Manifest 中的公开版本 |
| App 版本 | TestFlight 构建号或 App Store 版本 |
| 复现性 | always、intermittent、not-reproduced |
| 严重级别 | P0、P1、P2、P3 |
| 状态 | triage、reproduced、in-progress、verified、released |

不得把用户邮箱、截图或其他个人信息直接写入公开仓库 Issue。

## 5. 严重级别

| 级别 | 定义 | 例子 | 内部响应目标 |
| --- | --- | --- | --- |
| P0 | 大面积不可用、隐私或供应链安全事件 | 恶意规则包被接受、浏览数据被上传、所有用户无法浏览 | 立即停止发布并启动事故响应 |
| P1 | 核心能力大面积失效或高影响误伤 | 规则导致主流站点无法登录、规则更新普遍失败 | 当天确认影响，优先回滚或缓解 |
| P2 | 局部高频问题，有可行绕过方式 | YouTube 某一场景失效、特定站点需 Allowlist | 进入最近规则发布周期 |
| P3 | 低影响、低频或体验改进 | 小范围元素残留、非关键布局问题 | 纳入待办并按价值排序 |

这些是内部目标，不作为公开服务等级承诺。团队规模和正式支持政策确定后再决定是否公开 SLA。

## 6. 问题分诊流程

1. 确认 App、系统、规则版本和发生时间。
2. 判断是 `Site Broken` 还是 `Missed Ad`。
3. 使用无个人数据的测试环境复现。
4. 依次测试：
   - 暂停全部保护。
   - 将站点加入 Allowlist。
   - 仅关闭 Gleem Extra。
   - 切换到上一规则版本。
5. 归因到基础规则、自有规则、Extra 脚本、客户端、分发服务或第三方站点。
6. 评估影响范围与严重级别。
7. 选择规则例外、规则修复、脚本修复、App 修复或无需处理。
8. 在 staging 验证原问题及邻近场景。
9. 发布、灰度或回滚。
10. 回访提交者并更新 Issue。

无法复现时保留事实：记录已检查的环境、缺少的信息和临时绕过方式，不应直接关闭为“用户问题”。

## 7. 规则发布流程

### 7.1 常规发布

1. 固定上游规则版本。
2. 应用 Gleem 自有修复和例外。
3. 执行编译、格式、数量、许可证元数据和确定性检查。
4. 运行合成 fixture 与真实站点回归。
5. 生成规则包、哈希、Manifest 和签名。
6. 发布到 staging。
7. 在 iPhone、iPad 上验证下载、激活和回退。
8. 晋升到 production。
9. 记录规则版本、变更内容和验证结果。

### 7.2 紧急修复

紧急修复只用于 P0/P1 或明显大面积误伤：

- 优先加入最小站点例外或回滚，不进行大范围重构。
- 必须保留签名和完整性验证。
- 至少由另一名成员复核变更；单人团队则执行独立的第二遍 diff 与回归检查。
- 修复后补齐完整测试和事故记录。

### 7.3 回滚

触发条件包括：

- Site Broken 报告突然集中增加。
- 关键站点核心流程被破坏。
- 规则包无法加载或导致扩展失效。
- 哈希、签名或 Manifest 元数据异常。
- 无法在短时间内确认安全性。

回滚目标是重新发布最后一个已知可用的签名版本。不得直接关闭客户端校验来“恢复服务”。

## 8. 动态站点专项运营

YouTube 和 X 应拥有独立的变更记录和冒烟测试：

- 每次相关规则改动都检查未登录、测试账号登录和站内导航。
- 同时验证 Content Blocker 单独开启与 Gleem Extra 开启。
- 记录站点变化发生时间、受影响页面和临时限制。
- 修复不能依赖具体用户账号或收集真实时间线内容。
- 失效范围较大时，在产品支持页面或 TestFlight 更新中说明。

产品文案使用“针对当前已验证的 Safari 场景提供增强拦截”，避免使用“永久无广告”。

## 9. App 与分发服务故障

### 9.1 规则更新服务不可用

预期行为：

- 客户端继续使用最后一个通过验证的规则版本。
- 不反复弹窗打扰用户。
- 设置页可显示上次成功更新时间和当前版本。
- 达到合理重试窗口后采用退避策略。

### 9.2 Manifest 或规则包损坏

预期行为：

- 拒绝激活。
- 保留当前规则。
- 记录不含浏览数据的本地错误码。
- 若用户主动反馈，可附加错误码和版本信息。

### 9.3 Safari 扩展被关闭

预期行为：

- 首页显示 `Action Needed`。
- 给出准确的系统设置路径。
- 不声称设备仍处于保护状态。

## 10. 隐私与安全事故

以下情况直接按 P0 处理：

- 客户端或第三方 SDK 上传了未声明的浏览数据。
- 规则签名密钥泄露或疑似被滥用。
- 未授权规则包进入 production。
- 诊断信息包含 Cookie、凭据、完整浏览历史等敏感内容。
- 支持系统中的用户资料被未授权访问。

响应顺序：

1. 停止相关规则、构建或服务继续发布。
2. 保全必要证据，避免扩大敏感数据访问。
3. 撤销或轮换密钥，回滚到可信版本。
4. 确定影响数据、用户、时间和地区。
5. 咨询适用法律与 App Store 通知要求。
6. 用事实向受影响用户沟通，不弱化风险。
7. 修复后完成独立验证再恢复发布。
8. 形成事故复盘和预防行动。

任何法规通知时限和具体法律义务必须由适用地区的专业意见确认，本文不替代法律建议。

## 11. 用户沟通模板结构

问题确认：

- 我们确认了什么。
- 哪些版本或场景受到影响。
- 用户现在可以采取什么绕过方式。
- 下一次更新时间。

问题解决：

- 已发布的 App 或规则版本。
- 修复的具体场景。
- 用户是否需要操作。
- 仍存在的限制。

不要使用“已彻底解决”“100% 拦截”等不可验证表述。

## 12. 支持数据与保留

TestFlight 阶段采用最小化人工支持：

- 只保存处理问题所需的信息。
- 不把支持邮箱与浏览行为合并分析。
- Issue 中使用内部编号，不公开个人联系方式。
- 用户要求删除其反馈附件时，应能够定位和处理。

正式发布前必须确定并公开：

- 支持数据保留周期。
- 删除请求入口和执行流程。
- 第三方支持工具及其数据处理条款。
- 数据存放地区和访问权限。

在这些政策未定前，不写死未经法律与运营确认的保留天数。

## 13. 无用户分析时的健康监控

零数据承诺不等于完全没有运营信号。可以使用：

- CDN 的聚合可用性与错误率，配置为最小日志并避免稳定用户标识。
- App Store Connect 提供的聚合崩溃和安装信息。
- TestFlight 自带的崩溃反馈。
- 用户主动提交的问题。
- 团队定时执行的合成下载和签名验证。
- 固定站点的人工冒烟回归。

不得使用这些信号重建单个用户的浏览路径。

## 14. 事故复盘

P0/P1 结束后记录：

- 影响和时间线。
- 首次发现方式。
- 技术根因与流程根因。
- 为什么现有测试或发布门禁没有阻止问题。
- 回滚和恢复过程。
- 用户沟通情况。
- 可验证的预防行动、负责人和截止日期。

复盘关注系统和流程改进，不以追责个人为目的。

## 15. 上线准备检查

- 支持入口可用，用户能看到将提交的内容。
- 严重级别和负责人明确。
- staging、production 和回滚权限已最小化配置。
- 规则签名密钥未存入仓库。
- CDN 和签名验证合成检查可用。
- YouTube、X 冒烟脚本和设备已准备。
- 隐私事故联系人和内部升级路径已明确。
- TestFlight 已知问题和限制可被测试者看到。
- 正式发布前的数据保留与删除政策已完成。
