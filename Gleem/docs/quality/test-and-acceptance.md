# 测试与验收标准

## 1. 目的

本文定义 Gleem 在开发、规则发布和 TestFlight 交付前必须完成的验证工作。目标不是追求测试数量，而是确保用户最依赖的三件事真实成立：

1. Safari 广告与追踪器能够稳定拦截。
2. YouTube、X 等重点站点的增强拦截可用，失败时不会破坏基础浏览。
3. 产品不会在用户不知情的情况下收集或上传浏览数据。

## 2. 测试原则

- 以真实 iPhone、iPad 和 Safari 行为为最终判断依据，模拟器只用于提高开发反馈速度。
- 广告拦截率与误伤率必须同时评估，不能只追求“拦得更多”。
- 规则、客户端、远端清单分别测试，故障定位时不得混为一层。
- 任何远端规则更新都必须支持校验失败拒绝、保留上一个可用版本和快速回滚。
- 不依赖人工主观判断的行为应尽量自动化；动态站点仍需保留真实设备人工回归。
- 测试报告只记录必要结果，不收集测试者的完整浏览历史。

## 3. 测试层级

### 3.1 单元测试

客户端至少覆盖：

- 首页保护状态的状态转换。
- Safari 扩展启用状态的读取和映射。
- `Paused` 到期后的自动恢复。
- Allowlist 域名标准化、去重、添加和删除。
- App Group 配置读写和版本迁移。
- Manifest 解析、版本比较、过期判断。
- 签名校验成功、失败和密钥不匹配。
- 规则包完整性校验。
- 更新失败时保留当前可用规则。
- 用户主动生成诊断信息时的脱敏逻辑。

### 3.2 规则编译测试

每次规则构建至少验证：

- 输入源可读取，版本和许可证信息完整。
- 不支持的语法被明确拒绝或记录，不能静默产生错误规则。
- 编译结果符合 Safari Content Blocker 的格式与数量限制。
- 相同输入生成确定性一致的产物。
- 重复规则和明显冲突规则被检测。
- Allowlist 例外能覆盖对应阻断规则。
- 规则包、Manifest、哈希和签名相互匹配。
- 自有修复层的优先级高于上游候选规则。
- 编译失败不会覆盖上一版可发布产物。

建议为关键规则保留最小化的合成 HTML fixture，避免自动测试依赖实时网页结构。fixture 只复现必要 DOM 特征，不复制整页内容。

### 3.3 集成测试

至少验证以下链路：

1. App 下载 Manifest。
2. 校验 Manifest 签名与版本。
3. 下载规则包并校验哈希。
4. 原子替换本地规则。
5. 请求 Safari 重新加载 Content Blocker。
6. App 与扩展从 App Group 读取一致配置。
7. 更新任一步失败时回退到上一可用版本。

还需覆盖：

- 首次启动时离线。
- 更新过程中断网。
- CDN 返回超时、404、错误 MIME type 或损坏文件。
- Manifest 版本倒退。
- 设备时间明显错误。
- App 被系统终止后重新启动。
- 从旧版本升级后已有 Allowlist 和暂停状态仍然有效。

### 3.4 UI 与可访问性测试

关键流程需覆盖自动化或可重复人工脚本：

- 首次启动与 Safari 扩展开启指导。
- `Protected`、`Action Needed`、`Paused` 三种首页状态。
- 开启和撤销站点 Allowlist。
- 暂停保护并恢复。
- 查看规则更新时间和版本。
- Gleem Extra 权限说明及 youtube.com、x.com 授权流程。
- `Missed Ad` 和 `Site Broken` 反馈流程。
- Pro Preview 展示，不出现不可兑现的购买入口。

可访问性至少检查：

- VoiceOver 阅读顺序、按钮名称和状态描述。
- Dynamic Type 放大后不截断关键操作。
- 深色模式与浅色模式。
- Reduce Motion 开启时移除非必要动画。
- Increase Contrast 和 Differentiate Without Color。
- 横屏、分屏和 iPad 尺寸适配。
- 键盘焦点与外接键盘基本操作。

## 4. 真实站点测试矩阵

测试矩阵应按能力分类维护，不把某个第三方站点的当前表现永久写成产品承诺。

| 类别 | 重点观察 | 通过条件 |
| --- | --- | --- |
| 新闻与内容站点 | 展示广告、追踪请求、正文加载 | 广告明显减少，正文、图片和导航可用 |
| 搜索与工具站点 | 搜索、表单、重定向 | 主要功能不被规则破坏 |
| 电商站点 | 商品列表、详情、购物车 | 不因拦截导致核心交易路径失效 |
| 登录站点 | 登录、验证码、第三方登录 | 默认规则不阻断必要认证流程 |
| 媒体站点 | 播放器、字幕、全屏 | 内容可播放，控制器可用 |
| YouTube Safari | 播放前/中广告、页面占位、连续播放 | 在已支持场景中广告被抑制，失败时页面仍可用 |
| X Safari | Promoted Posts、时间线滚动、详情页 | 推广内容被隐藏，正常帖子和交互可用 |
| Annoyances | Cookie banner、Open in App、newsletter、anti-adblock | 已支持元素被处理，不遮挡主体内容 |
| Allowlist | 单站点关闭保护 | 目标站点恢复原始行为，其他站点不受影响 |

### 4.1 高风险路径

银行、支付、医疗、政府、身份验证等站点以“不破坏”为首要目标。MVP 不对其广告拦截效果做强承诺；发现兼容性问题时可先加入安全例外，再评估精细规则。

### 4.2 动态站点回归

YouTube 和 X 的结构可能频繁变化，应建立独立回归清单：

- 未登录与已登录状态。
- 首页、搜索、详情和连续浏览。
- 普通窗口与无痕浏览。
- 页面首次载入与站内导航。
- 网络较慢时的加载行为。
- Content Blocker 单独启用和 Gleem Extra 同时启用。

使用测试账号时不得包含真实个人资料。测试记录不得保存完整浏览历史或身份凭据。

## 5. 设备与系统矩阵

发布前至少在以下形态验证：

- 一台当前主流尺寸的真实 iPhone。
- 一台较小屏幕或较旧但支持 iOS 26 的真实 iPhone。
- 一台真实 iPad，并检查横屏和分屏。
- iOS/iPadOS 26 当前公开稳定版本。
- 若 TestFlight 周期内出现新的 26.x 版本，应完成冒烟回归。

实际设备型号、系统版本、Safari 版本和测试日期记录在当次测试报告中，不在本文写死。

## 6. 性能与稳定性

MVP 需要建立可比较的基线，具体阈值以真实设备首轮测量后确定。至少记录：

- App 冷启动和首页可交互时间。
- 规则下载、校验、落盘和重新加载耗时。
- 规则包磁盘占用。
- 更新期间的峰值内存。
- Safari 开启规则前后，典型页面的可交互时间与视觉稳定性。
- 连续浏览和多标签页下的崩溃、卡顿与扩展失效情况。

不得为了展示效果伪造“节省时间”“拦截数量”或“减少流量”等指标。没有可靠本地测量时不显示。

## 7. 隐私与网络验证

使用代理抓包或系统网络日志验证：

- 正常浏览时 Gleem 不上传访问 URL、域名、页面标题或请求日志。
- 客户端只访问已声明的规则分发端点和 Apple 必要服务。
- 诊断信息只在用户明确点击发送后生成或分享。
- 诊断内容不包含完整 URL、Cookie、账号标识和页面正文。
- 规则 CDN 不通过自定义查询参数创建稳定用户标识。
- 关闭自动更新后不会继续进行自有规则更新请求。

该验证必须在真实设备上至少执行一次，并保留经过脱敏的验证记录。

## 8. 反馈问题验收

### 8.1 Missed Ad

提交前向用户展示将分享的内容。MVP 建议仅包含：

- 用户主动填写的站点域名或问题描述。
- Gleem 版本、规则版本、设备类型和系统版本。
- Content Blocker、Gleem Extra 是否启用。

不自动附带完整 URL、截图或网页内容。若需要截图，必须由用户主动选择。

### 8.2 Site Broken

除上述信息外，需引导用户验证：

1. 临时暂停后问题是否消失。
2. 加入 Allowlist 后问题是否消失。
3. 仅关闭 Gleem Extra 后问题是否消失。

该结果用于区分基础规则、增强扩展和非 Gleem 原因。

## 9. 两周 TestFlight 验收门槛

第 14 天提交私有 TestFlight 构建前，必须满足：

- App 可安装、可启动，无已知阻断级崩溃。
- Content Blocker 能按引导启用，并正确显示实际状态。
- 基础广告、追踪器和 annoyances 规则已在真实设备验证。
- YouTube 与 X 的增强能力完成定义内场景验证，限制已在产品内说明。
- Allowlist、暂停、自动恢复和规则更新可用。
- 签名、哈希校验、失败保留旧版本和回滚链路已验证。
- `Missed Ad`、`Site Broken` 能以用户主动方式提交或导出。
- 无账号、无分析 SDK、无浏览日志上传。
- 隐私说明、扩展权限说明和 TestFlight 测试说明已准备。
- 所有 P0、P1 问题关闭；P2 问题有明确影响说明和处理决定。

若外部 TestFlight Beta App Review 尚未完成，第 14 天的交付定义为“构建已上传并可供内部测试，外部测试已提交审核”，不得把 Apple 审核等待伪报为已对外发布。

## 10. 后续 Pro 技术验证

`NEURLFilterManager` 和 Apple Private Information Retrieval 不属于首个两周 TestFlight 范围。进入验证阶段后，需新增：

- 系统能力资格和 entitlement 验证。
- URL Filter 在目标系统与地区的实际可用性。
- 规则查询正确性、时延、缓存和离线行为。
- Apple OHTTP relay 依赖异常时的降级方式。
- 原生 App 流量兼容性和误伤恢复。
- 不解密 HTTPS、不读取内容的边界验证。
- 对原生 YouTube、X 广告不作保证的产品文案检查。

## 11. 测试结果记录

每次候选构建至少记录：

- 构建号、Git commit、规则版本和 Manifest 版本。
- 设备与系统矩阵。
- 已执行用例、通过结果和未执行原因。
- 已知问题及严重级别。
- 是否允许进入下一环境。
- 验收人和日期。

测试记录可以使用 Issue、Release Checklist 或团队现有工具，不要求为每次测试新增仓库文档。
